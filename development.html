01 · roadmap

Roadmap

Five steps, from a first bootable image to a first stable public release. The first three take their codenames from Spanish almond varieties; 0.5 and 1.0 have not been named yet. Nothing here is marked done, because nothing is done yet.

versionmilestonestatus
  1. Almond 0.1 ‘Marcona’ First bootable Debian-based ISO Status: In progress Build configuration drafted with Debian live-build. No ISO has been built yet.
  2. Almond 0.2 ‘Largueta’ Custom Almond branding, wallpaper, themes, and system identity Status: Planned
  3. Almond 0.3 ‘Valencia’ Customized desktop experience Status: Planned
  4. Almond 0.5 Graphical installer and testing Status: Planned
  5. Almond 1.0 First stable public release Status: Planned

How a milestone counts as done

Every milestone has a list of evidence it has to produce before it is marked done. Until that evidence exists, the milestone stays ‘In progress’ or ‘Planned’, however close it looks.

For 0.1, that means an ISO hash, a build log, a package manifest, and repeated boot, networking and terminal checks.

02 · definition of done

Definition of done

A milestone is done when it can be shown to work, not when it seems to.

This is the evidence each step has to produce first. It is written down before any of the work is finished, so it is clear in advance what each step has to show.

What has to be shown before a milestone is marked done
VersionEvidence required before it is marked done
0.1 ‘Marcona’An ISO hash, a build log and a package manifest; repeated boot, networking and terminal checks.
0.2 ‘Largueta’An original, licensed logo and wallpaper; a contrast review of the colour palette; screenshots.
0.3 ‘Valencia’Usability and regression checks of the layout, the launcher, the settings and software management.
0.5Installs on disposable disks; account and permission tests; updates that persist; bootloader and recovery validation; a security review.
1.0A published support matrix; maintained updates; release, source and license materials; reproducible build instructions; a support process.

03 · technical direction

Technical direction

Almond starts from Debian and will be built with Debian’s own tools.

This is the direction for now. None of it has been tested on a finished image, because there is no finished image yet.

Debian underneath

The planned base is Debian Stable, currently Debian 13 ‘trixie’. Almond’s own work will sit on top of Debian’s packages, and every upstream package keeps its own license.

Built with live-build

Images will be built with Debian live-build, Debian’s tool for building live system images. The first draft of the build configuration targets a 64-bit ARM (ARM64) UEFI virtual machine. It has not produced an image yet.

Virtual machines first

Every build will be tested in a virtual machine before it goes near real hardware:

  • QEMU-based tools, such as QEMU/KVM or UTM;
  • VirtualBox, where it supports the architecture.

ARM64 is not Apple hardware

The ARM64 virtual machine is only the first target in the drafted configuration. Generic ARM64 support does not mean support for Apple hardware, and native installation on Apple Silicon Macs is not a goal of any planned version.

Long term: going independent

Debian is the starting point, not the destination. Versions 0.1 to 1.0 are built on Debian Stable. After that, Almond plans to replace what it borrows, one layer at a time:

  1. An Almond package repository for Almond’s own software, on top of Debian.
  2. Building packages from source on Almond’s own build system.
  3. A fully independent Almond, no longer based on Debian.

Independence has a real cost: every package then needs its own maintenance, security fixes and build servers. Each step will only start once the one before it works and can be maintained. No dates are promised.

04 · editions

Editions: open decisions

Two editions are defined: AALLDM for newer PCs and AALDM for older and low-power 64-bit PCs. Most of what will set them apart has not been decided yet.

These are the open questions for each one, listed so that nobody mistakes a plan for a decision. Which edition reaches 0.1 first has not been decided either.

When we say an edition is light or fast, we will publish the numbers behind it – idle memory, boot time, disk use – with the method, so anyone can repeat the test.

05 · development log

Development log

Dated entries for things that have actually happened, newest first. Plans live on the roadmap above; this list is only for what is already true.

  1. 14 Oct 2026 First public repositories published on GitHub under the MIT License: almond-linux (the build configuration) and almondlinux.github.io (this website).
  2. 14 Oct 2026 Long-term direction decided: start on Debian, then become a fully independent distribution step by step.
  3. 14 Oct 2026 Release codenames chosen from Spanish almond varieties: ‘Marcona’ for 0.1, ‘Largueta’ for 0.2 and ‘Valencia’ for 0.3.
  4. 14 Oct 2026 Two editions defined: AALLDM for newer PCs and AALDM for older and low-power 64-bit PCs.
  5. 14 Oct 2026 The AlmondLinux organisation is created on GitHub.
  6. 14 Oct 2026 The almond logo is adopted as the official mark.
  7. 14 Oct 2026 First draft of the build configuration written: a live-build setup for an ARM64 UEFI virtual machine, a desktop package list, an image-identity hook and a guarded build script. Checked so far: shell syntax, and that the build script refuses to run outside Linux. Not yet checked: package resolution, image generation, booting, networking, security defaults and installation.

Newest first. That’s the whole log so far.
